# 现有能力分类表（首版）

## 目标

明确现有项目能力在“主线总控 Agent”新口径下，哪些继续保留，哪些降级为非核心，哪些逐步迁移到新主线，哪些暂不进入当前核心范围。

## 分类原则

1. 能支撑“主目标接管、证据闭环、风险判断、现实调度”的能力优先保留或迁移。
2. 泛能力、陪聊型能力、无明确结果压力的能力默认降级。
3. 现有必要基础设施不做破坏式删除。

## A. 保留为基础设施

### 运行时与工程底座

1. Runtime 主链路
2. 会话、日志、配置、模型切换
3. 工作区、文件、命令等基础能力
4. 现有知识、记忆、verify、browser 等能力池

### 原因

这些能力是后续新总控系统的可挂接底座，不应在产品语义切换时被误删。

## B. 迁移为新核心组成

### 需要逐步迁移到新主线的能力

1. 首页主入口叙事
2. 状态可视化
3. 风险判断展示
4. 任务优先级与下一步建议
5. 关键证据录入与验证

### 目标

这些能力后续不再只服务“会话式智能体”，而要服务“主线总控 Agent”。

## C. 降级为非核心但继续保留

### 默认降级项

1. 泛问答
2. 日常陪聊
3. 长期人生规划
4. 价值观讨论
5. “什么都可以先聊聊”的开放型入口

### 处理方式

1. 不删除能力
2. 不作为桌面插件首页主叙事
3. 不抢占主目标、概率与证据入口的位置

## D. 暂不纳入本轮核心

### 可以后续再评估的项

1. 高复杂度长期个性化建模
2. 多主线并发治理
3. 全量自动化执行接管
4. 高资源常驻的复杂前端面板

### 原因

这些能力当前会增加实现复杂度，但不会提升 V1 第一验证目标。

## E. 当前最需要保护的旧能力

1. 现有运行时不应因新定义而停摆
2. 现有日志、历史、知识、记忆资产不应丢失
3. 现有会话与模型配置链路不应被破坏

## F. 后续落地建议

1. 产品入口先切换叙事，再切实现
2. 能力先分类、再重排、后迁移
3. 任何旧能力降级时，先补“为何非核心”的说明，不直接默删
