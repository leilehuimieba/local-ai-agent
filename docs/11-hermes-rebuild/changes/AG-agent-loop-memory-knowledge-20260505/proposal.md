# 变更提案

## 背景

- 当前项目已经具备稳定的单次运行主链：`Analyze -> Plan -> Execute -> Observe -> Verify -> Finish`，并且 checkpoint、confirmation、artifact、MCP 接入都已成立。
- 当前薄弱点不在“有没有壳”，而在“壳能否支撑更复杂的 agent 任务”：多步回路仍偏单动作收口，记忆可存可回但路由还偏弱，知识检索能命中但还不够支撑高质量回答，验证更偏统一摘要检查而不是任务类型化验收。
- 结合外部知识沉淀，下一阶段最值得投入的不是继续扩 provider 或 UI，而是把 Runtime 提升为“复杂任务也能稳住”的 agent 执行骨架。

## 目标

- 给当前项目产出一份可直接交给实现型智能体执行的优化蓝图。
- 明确 Runtime 回路、上下文装配、记忆路由、知识检索、验证闭环五个方向的最小收口路径。
- 明确每个方向应优先改哪些模块、先补什么字段、需要什么事件、如何验证。

## 非目标

- 不在本 change 内直接实现所有能力。
- 不提前引入复杂多智能体编排。
- 不以“扩更多工具 / 更多 provider / 更复杂 UI”替代 Runtime 主干优化。
- 不重做当前 Rust / Go / Frontend 边界。

## 验收口径

- 文档能够明确回答：
  - 当前补的是哪几层壳；
  - 每一层壳的目标状态是什么；
  - 先改哪些文件；
  - 每一步的验证证据是什么；
  - 哪些高级能力明确后置。
- 文档足够具体，后续智能体可以据此拆成实现 change，而不需要重新做一轮大范围诊断。
