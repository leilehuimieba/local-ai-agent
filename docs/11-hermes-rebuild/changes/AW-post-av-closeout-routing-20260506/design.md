# 设计说明

## 1. 范围边界

本 change 只做“后 `AV` 收口路由”：

1. 活跃 change 切换；
2. 收口状态同步；
3. 剩余未提交改动主簇判断；
4. 下一实现入口裁决；
5. 未提交工作区的归属矩阵与建议入库顺序。

不进入新的运行时实现。

## 2. 执行方式

### 2.1 先确认 `AV` 已满足收口条件

依赖以下证据：

1. 三个原始热点文件均已低于 600 行红线；
2. `AV` 聚合验证全绿；
3. `AV` 范围未扩出 memory 写回治理簇；
4. `AV` 文档已补齐到“可切换下一主推进项”。

### 2.2 再判断剩余工作区是否构成新的实现主簇

用以下材料判断：

1. `git status --short`
2. `git diff --stat`
3. 已存在 change 的 `status.md / verify.md`
4. `archive/2026-05-06/INDEX.md`
5. `git diff --name-only`
6. `git ls-files --others --exclude-standard`

判断准则：

1. 如果剩余改动仍明显属于某个单一能力簇，才允许切新的实现 change；
2. 如果剩余改动主要是多 change 的收口、归档准备与状态不一致，则继续保持 routing change，不误开实现项。

### 2.4 归属矩阵与入库顺序

在确认“当前不切新实现项”之后，再补一份正式的未提交改动归属矩阵：

1. 所有已修改 / 未跟踪路径必须尽量挂回既有 change；
2. 对混合文件只给“主归属 + 次级关联”，不强拆成新的实现项；
3. 建议入库顺序优先按：
   - 状态口径
   - 已完成 change 文档 / 证据
   - 结构治理代码
   - 浏览器残余
   - 知识回答资产
   - 历史状态回写

本轮新增产物：

- `D:/newwork/本地智能体/docs/11-hermes-rebuild/changes/AW-post-av-closeout-routing-20260506/ownership-matrix.md`

### 2.3 状态切换顺序

1. 先更新 `current-state.md`
2. 再更新 `changes/INDEX.md`
3. 再更新 `AV/status.md`
4. 最后把 `AW` 五件套补齐

## 3. 当前判断

当前工作区剩余未收口改动更像：

1. 多个已完成 change 的未提交混合态；
2. 文档 / 脚本 / 证据 / archive 入口尚未完全统一；
3. 不足以支持“立即切下一把实现型 change”。

因此当前正确动作是：

1. 把 `AV` 切为已收口；
2. 把 `AW` 设为当前活跃 change；
3. 在 `AW` 内继续做下一主推进项裁决，而不是直接编码；
4. 在 `AW` 内补未提交改动归属矩阵与建议入库顺序，防止后续继续混做。

## 4. 风险与回退

### 风险

1. 误把尚未收口的混合工作区判断成新的实现主簇；
2. 继续让 `current-state.md` 与真实状态不同步；
3. 在未完成状态切换前再次进入大规模实现。

### 回退

1. 若后续发现已有明确实现主簇，可在 `AW` 内只做裁决并立即切换；
2. 若 `AW` 的判断与后续证据冲突，以实时 `git status / git diff` 为准重新修正；
3. `AW` 本身不改业务逻辑，因此回退成本仅限文档状态修正。
